# 08 · 扩展设计：从当前闭环走向可维护产品

[部署](07-deployment.md) · [总目录](../../README.md)

本章是后续设计，不将计划写成已实现能力。重点讨论四个直接影响当前代码的方向，再补上线优先级与评测。

## 1. 消息管理：先区分“模型少看”与“状态删除”

推荐流程会产生工具申请、结构结果、查询结果和纠错消息，反复多轮后历史变长。可以先在模型调用前选择相关消息，而不是立刻从 State 删除；前者减少本次 token，后者改变持久化历史与后续执行。

需要真正裁剪状态时，工具请求与 ToolMessage 必须成对处理，不能留下悬空调用。摘要应覆盖稳定用户需求与关键查询事实，不机械保留大段原始结果，也不能把摘要当成可随意覆盖真实业务记录的权威来源。

合适位置可能是推荐子图结束后、主图进入是否预约前，但应确保已完成的回答仍可展示，挂起的工具协议没有被破坏。

## 2. 需求字段标准化：结构化并不等于能落库

当前抽取 room_type、orientation 等自由字符串。用户说“一室一厅”和数据源中某个枚举不一定天然相同。

可增加“抽取 → 标准化 → 校验 → 查询计划”层，保留用户原表达与标准值，并为不支持的取值提供追问。不要让提示词单独承担所有映射，也不要硬编码一组未经数据定义确认的枚举。

验收时分别测试语言抽取正确性与标准化正确性，否则 SQL 没结果时难以知道是数据缺失还是映射错误。

## 3. SQL 执行前加人工审阅

候选插入点：`check_query → review_sql → run_query`。审阅内容包括查询意图、参数与风险，用户可以通过、修改或拒绝。

修改 SQL 后，要同步修改待执行 AIMessage 的工具参数并保持请求/结果配对。拒绝时不能让一条未响应 tool call 留在消息历史里继续请求模型；需要定义明确的取消结果或移除未执行请求的策略。

人工审批解决“人确认这次要做什么”，最小权限、超时与结果上限解决执行约束，两者不能替代。

## 4. 自定义执行进度

当前主要使用 updates/messages。新增 custom stream 时，应输出稳定、可公开的结构化事件：阶段、状态、短消息和请求关联标识。

把“正在获取结构”“查询完成”“等待你确认”从普通模型文本中分离，前端可以用时间线展示。不要直接暴露日志、身份证或内部推理；事件设计应与业务观察目标一致。

## 5. 重放与幂等：真正订单服务需要什么

UUID 让工单号随机唯一，却不让同一业务请求只执行一次。幂等需要请求唯一键与服务端约束：重复请求读回同一订单，而不是再产生一个 UUID。

还需要房源唯一标识、状态校验、库存与订单事务。以标题字符串做真实房源主键并不可靠；电话/身份格式也需要规则验证与敏感数据保护。

## 6. 长期偏好的并发一致性

`search → deepcopy → append → put` 是合理的数据处理顺序，但两个并发运行仍可能读到同一旧值，最后一次写覆盖前一次。可选方案包括稳定唯一 key、版本号比较、事务或独立的预约明细存储。

选择哪种方案取决于业务访问模式，不应把 Store 的通用 KV 接口当成自动提供任意事务的业务数据库。

## 7. 测试与评测分层

| 层 | 测什么 | 不要用什么替代 |
| --- | --- | --- |
| 普通逻辑 | 合并、0、None、序列化 | 只观察一条聊天结果 |
| 图控制流 | 分支、中断、恢复、终止 | 只成功 compile |
| 模型任务 | 意图、字段、调用选择 | 只看结构化 JSON 能解析 |
| 数据查询 | SQL 与结果事实一致 | 只看没有报错 |
| 前端协议 | 分块、重复事件、断线状态 | 只测完整单块数据 |
| 集成 | 真实模型/DB/服务端联动 | 内存假模型测试 |

指标应从有标注用例和真实测量得到；不提供没有测试过的准确率、成本降低或高并发数字。

## 8. 优先级与验收条件

1. 完成真实模型与数据源集成回归，冻结依赖与镜像基线。
2. 认证用户、授权访问 thread/Store，并建立 SQL 执行约束。
3. 将模拟工单接到幂等业务服务。
4. 拆分中断前抽取，减少重放中的重复模型调用。
5. 管理历史消息、规范字段、增加可审阅查询与清晰进度。

每项都需要可观察的验收标准：拒绝越权、重复请求只一单、缺字段继续问、查询超时受控、并发追加不丢失。这样演进方向才能转化成工程任务。
