# 开发问题与处理思路

[项目文章](../README.md) · [实现详解](implementation.md) · [测试](testing.md)

Agent 的问题不全发生在模型里。这个项目把问题分成四层：业务字段、消息协议、持久化边界、传输与部署。定位时先确定错误在哪一层，再决定是继续追问、重新生成，还是直接修复程序或配置。

## 1. 用户补了信息，流程为什么还不能继续

**现象**：输入预算后，仍收到补充提示，或后续查询缺少条件。

**原因**：用户输入是一段文本，流程依赖的却是抽取后的字段。可能仍缺城市，只抽出预算的一侧，或者客户端没有恢复正在等待的 thread。

**实现思路**：每次补充后重新抽取并合并，使用城市与预算两端的完整性判断控制循环；前端根据 pendingInterrupt 向同一 thread 发送 resume。

**验证**：先发模糊需求，再只补城市，确认系统继续等待预算；最后补 0–1500，确认采集结束且保留 0。该路径使用实际采集节点与内存检查点测试。

结构化输出只能约束字段形状，不能保证所有用户表达都被理解。单位换算、上下界顺序与区域映射需要进一步业务校验和评测。

## 2. 合法的 0 为什么变成默认值

**现象**：用户说“1500 以内”，最低预算被当成没提供。

**原因**：`if not value` 会把 0、None、空字符串都视为假，但这些值的业务含义不同。

**实现思路**：数值缺失使用 `is None`；合并历史预算时明确比较上下界；序列化只排除 None，不排除 0。

**验证**：覆盖空历史、仅预约历史、0 下界及更宽/更窄的新预算，确认查询条件和历史区间遵循不同策略。

## 3. 预约摘要在内存中正常，为什么写 Store 出错

**现象**：列表可以 append，但持久化或 JSON 编码失败；或者出现对 None 调用 append。

**原因**：Pydantic 对象不是普通 JSON 值；`setdefault` 也只处理“键不存在”，不能处理“键存在但为 null”。

**实现思路**：在持久化边界统一调用 `model_dump(mode='json', exclude_none=True)`；用 `prefs.get('reserved_info') or []` 处理空值；复制旧记录后再合并，避免隐式修改。

**验证**：预约工具连续调用两次，确认同一用户仍是一条偏好记录，内部有两条可 JSON 编码的预约摘要；分别覆盖空字典、null 列表和已有列表。

## 4. 为什么一次 SQL 检查会导致消息协议错误

**现象**：数据库工具还没有真正执行，模型 API 已提示工具调用缺少对应响应。

**原因**：查询生成与检查各产生一条 AI 工具请求，但只执行最后一条，旧请求悬空。

```text
错误链：AI 请求 A → AI 请求 B → Tool 仅回答 B
目标链：AI 请求 B → Tool 回答 B
```

**实现思路**：检查节点沿用旧 AIMessage 的消息 ID，让 `add_messages` 替换待执行请求。ToolMessage 仍用真正的工具调用 ID 配对。

这里最容易混淆的是两类 ID：消息 ID 服务于历史合并，调用 ID 服务于请求/结果配对。不能靠把所有 ID 随意改成一样来修复。

**验证方向**：检查实际消息序列与调用 ID；图能够编译并不证明所有供应商的工具协议都兼容，真实模型集成仍需单独验证。

## 5. 中断恢复为什么会重复执行代码

**现象**：补充输入后，日志、模型抽取或某个外部动作又发生一次。

**原因**：恢复时重跑中断节点，框架在相应 interrupt 位置提供恢复值，并不是继续一段保存在内存中的 Python 调用栈。

**设计处理**：将有明确结果的步骤尽量拆成节点，保持 interrupt 顺序稳定；对订单等副作用设计业务幂等，而不是仅依赖“按钮只点一次”。当前采集节点仍可能重复模型抽取，后续拆分的目标是减少这部分非确定性。

**验证**：三个预约采集节点依次恢复，并确认最终状态中标题、电话、身份字段来自对应恢复值。订单幂等尚未实现，不能由这个控制流测试推导出来。

## 6. 用户已有记录，为什么还会 KeyError

**现象**：能够查到偏好记录，但读取预算字段时报错。

**原因**：记录存在不代表每个可选字段都存在。用户可以先预约，Store 中只有预约摘要，没有预算。

**实现思路**：可选字段用 `.get`；把合并逻辑从模型节点中抽成普通函数；保留旧预约信息，只更新预算相关字段。

**验证**：用仅包含 `reserved_info` 的历史输入合并预算，确认不会报错，也不会丢预约列表。

## 7. 流式接口为什么会偶发丢字或 JSON 解析失败

**现象**：同样的请求有时能显示，有时半条消息丢失，中文出现乱码。

**原因**：网络 chunk 的切分不保证与事件、行、JSON 或 UTF-8 字符边界一致。

**实现思路**：流式 TextDecoder 负责字节到字符，SSEParser 负责字符到事件，以空行完成一帧，再 JSON.parse。事件类型与 data 都要跨 chunk 保存。

**验证**：对包含中文、心跳、子图事件和多行 data 的同一字节流，在每个位置切成两段，并逐字节传入。112 个检查全部通过。

当前解析器处理传输分块，不负责断线后的自动重连与业务状态对齐，这两个问题需要 thread 状态查询和更完整的客户端设计。

## 8. 同一轮对话为什么可能创建多个 thread

**现象**：用户打开聊天或快速发送后，看起来像进入了不同会话。

**原因**：创建操作未完成时再次触发创建，或者一轮执行中允许重复发送。

**实现思路**：使用共享 `creating` Promise 合并并发创建；`busy` 阻止运行中重复提交；将是否恢复中断保存在明确变量中，避免依赖 DOM 顺序。

浏览器刷新后的 thread 恢复仍是独立问题，不能仅通过防抖解决。当前页面刷新会创建新 thread。

## 9. 本机能连数据库，容器里为什么不行

**现象**：本机 Python 能连接，Docker API 启动失败；或者 API 端口直接拒绝连接。

**原因**：容器里的 localhost 指容器自身；API 也可能因为数据库或模型初始化失败而退出，因此外部端口没有可用进程。

**排查顺序**：

1. `docker compose ps` 确认进程状态。
2. `docker compose logs --tail 100 langgraph-api` 找到首个启动错误。
3. 核对容器到 Windows 主机的 host.docker.internal、数据库监听、端口和账号权限。
4. 最后检查前端 apiBase 和 CORS，而不是一开始就修改浏览器代理。

`.env.local` 修改后应重新创建 API 容器；单纯 restart 不会重新读取新的创建环境。

## 10. 健康检查正常，为什么没有聊天页面

API 根路径或 `/ok` 返回健康 JSON，说明访问的是后端。前端由静态服务提供，地址是 `http://127.0.0.1:8080/house.html`，聊天入口为浮动气泡。

还要继续验证真实模型与 MySQL 调用。健康响应不等于业务链路通过，也不等于页面已经连接到正确的 API。

## 定位问题的固定顺序

```text
连接是否成功
    → HTTP 请求体是否被接受
    → 执行到了哪个节点
    → State 字段是否符合预期
    → 消息/工具请求是否配对
    → 持久化值是否可序列化
    → 最终回答是否符合数据事实
```

把错误留在所属层处理，才能避免通过增加提示词去掩盖配置或协议问题。
